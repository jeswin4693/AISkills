# Roadmap

SkillForge AI does three things, built in this order:

```
 Repo --> UNDERSTAND --graph facts--> SUGGEST --ideas with evidence--> BUILD --> skill packages
          (no AI)                     (AI + graph)                      (AI + templates)
```

| Slice | What | Status |
|---|---|---|
| A. Understand | Repository graph: functions, calls, imports, impact, duplicates, hotspots, dead-code candidates. Python + TypeScript/JavaScript. Incremental cache. CLI. Tests. See [graph.md](graph.md). | **Built** |
| B. Providers + Suggest | One `LLMProvider` interface (Gemini and OpenAI through one adapter, plus a mock for tests). A review pass and an ideas pass over a fact sheet from the graph. Every suggestion must cite real graph nodes; uncited ones are dropped. See [suggest.md](suggest.md). | **Built; 83 offline tests; verified live with Gemini** |
| C. Build | Requirement text, clarifying questions (completeness decided by a checklist, answers backed by verified quotes), approval, skill definition, generated files, `report.md`. A suggestion can seed it. See [build.md](build.md) (original plan: [step1-proposal.md](step1-proposal.md)). | **Built; 127 offline tests; verified live with Gemini** |
| D1. Safety | Static validators for any skill folder (hidden text, attack wording, scripts versus declared permissions, structure) run on every build; a Docker sandbox runner that fails closed. See [validate.md](validate.md). | **Built and proven: 14 real-container tests (Docker in WSL) prove the locks and the per-language runs; 232 tests in total** |
| E. Any language | The graph, validators and sandbox work beyond Python and TypeScript: 45 languages at three honest levels (full, standard, basic), Java/Go/Rust/C/C++/C#/Ruby/PHP/Kotlin with resolved imports and calls, grammars loaded on demand with an offline mode, interpreter languages runnable in the sandbox. See [languages.md](languages.md). | **Built and tested** |
| F. Scripts | `build --scripts`: the model writes helper scripts and test cases, code checks them, every case runs in the sandbox, one repair attempt shown the real output. A case passes only if it ran; untested scripts make the skill a DRAFT. See [scripts.md](scripts.md). | **Built; 273 tests in total (36 offline script tests, 5 more real-container tests); verified live: real containers and Gemini** |
| G. Library | `library import` (static checks first, refused if one fails; folders and untrusted zips), numbered versions with a SHA-256 manifest (tamper-evident), `diff`, `rollback` (adds a version), deterministic `export` zip, `install` to `.claude/skills` (explicit target, backup before `--force`), opt-in `--test-scripts` re-run in the sandbox. See [library.md](library.md). | **Built and tested; checked on the real CLI on Windows; not yet used on skills from other people** |
| H1. API | Local HTTP API (FastAPI, `serve`, 127.0.0.1 only): library, validate, sandbox status and languages endpoints; Host and Origin checks against DNS rebinding and cross-site requests; capped in-memory uploads. See [api.md](api.md). | **Built and tested; checked against a real running server (curl)** |
| H2. Database + builder sessions | SQLAlchemy + Alembic (SQLite first, one URL setting for another database); the skill builder as a session across requests: questions, answers, approval, then background jobs with progress, retry, save to the library. Same rules as the CLI (checklist in code, verified quotes, approval before building). See [database.md](database.md), [api.md](api.md). | **Built and tested (offline, incl. real threads); verified live with Gemini: a full conversation produced a skill with 21 checks passed. Not tried: PostgreSQL, building with scripts over HTTP with a real sandbox** |
| H3. Web UI shell + Library | `frontend/`: Next.js 16 + React 19 + TypeScript + Tailwind 4. App shell with a live status panel; Library page (import by choosing or dropping a .zip, results in plain words, refusals with the failed checks); skill page (versions, files, checks, export, install, restore); compare page (diff). See [ui.md](ui.md). | **Built; typecheck clean, 20 unit tests, and 19 behaviours checked in a real Edge browser against the real API; not tested in other browsers or with a screen reader** |
| H4. Builder page | `/builder`: describe a skill, answer only what is missing, approve a requirement shown beside the person's own verified words, watch the build, see each acceptance criterion beside the tests that cover it, save through the checked import. Model not set up, failures with retry, DRAFT gating, past sessions, discard. See [ui.md](ui.md). | **Built; 39 unit tests and 31 real-Edge behaviours with a scripted fake model; verified live once (2026-11-19): the whole conversation in a real browser against real Gemini, 21 s, saved as v1. Not verified: the scripts checkbox with a real sandbox, other browsers** |
| C1. Task Plan | `skillforge plan "<task>" --repo <path>`: reads a request and plans it before any work: what it contains (verified quotes) and does not say (questions, assumptions), the tier from measured graph facts, the process phases and stop triggers, the rules that apply (file:line, not enforced yet), and a token plan (named functions as exact line ranges, capped tests, a budget). Read-only; `--no-ai` sends nothing. See [task-conductor.md](task-conductor.md). | **Built; 79 offline tests; run live once with Gemini on this repo (and that run exposed and fixed two weaknesses). Not built: answering and approving a plan, a web page, turning plans into skills, enforcement** |
| I. Risk diff + rescan | The first differentiator ([differentiators.md](differentiators.md)): every new version of a skill is compared with the one before and **what got riskier is listed** (scripts that gain the network or commands, new permissions, attack-like wording and hidden markup, new web addresses, a changed description), and `library rescan` runs today's checks on every stored version. Code only, no model, nothing is run; it never says "safe". CLI (`diff`, `import`, `rescan`), API (`/diff`, `/import`, `/api/rescan`) and the Library, skill, Compare pages. See [library.md](library.md). | **Built; 47 offline tests (pure comparison, rescan, CLI, API); 38 behaviours in a real Edge browser, 7 of them new; mutation-checked (4 deliberate breaks, 1 survived and a test was added). Tested on synthetic skills only: the false-alarm rate on real skills is not measured** |
| J. Stronger skills | The builder writes skills that **work better and cost less to use**: the description is built by code from trigger phrases (so it says *when* to use the skill); your approved rules, acceptance criteria and failure behaviour are carried into SKILL.md word for word and checked; a worked example; what is only for people (limitations, permissions) moved to the README; quality checks for vague wording, inputs no step uses, outputs no step makes, over-long steps and garbled examples; the one repair attempt also fixes quality warnings and never makes the skill worse; the token cost (always loaded / when used / on demand) in every result. See [build.md](build.md). | **Built; 33 new offline tests (555 in all), 2 new UI unit tests and 1 new browser behaviour, 7 deliberate code breaks all caught; checked live with Gemini twice on the same job as an installed skill (SKILL.md about 392 to 404 tokens against 536, and the live runs exposed three weaknesses that were then fixed). Not measured: whether an agent does the job better with the new skills (test cases are still never run against an agent); the always-loaded text grows by about 11 to 20 tokens** |
| K. Test harness | `skillforge eval <folder>` and `build --eval`: a skill's own test cases are run against a model **with the skill and without it**, and code grades the replies with seven kinds of simple check (no model judges). It says whether the skill helped, adds nothing for its tokens, made things worse, or had too few cases; a skill that fails its own tests gets one repair shown the real replies. Every built test now carries the exact message to send and its checks. Text-only skills only (a model with no tools is not an agent). See [evaluate.md](evaluate.md). | **Built; 66 new offline tests (626 in all), 9 deliberate code breaks all caught; run live with Gemini on the commit-message job: with the skill 6 of 6, without it 2 of 6, because without it the model breaks the person's own 50-character rule (single runs vary: 0 of 3 once). Not built: running it from the web pages; tools-using skills; a stronger or independent judge of tone and facts. The tests are written by the model that wrote the skill** |
| L. AI engine | One model service for every builder ([ai-engine.md](ai-engine.md)): the model is chosen by kind of work (fast, design, code, actor) from optional settings, with Gemini the default for all of them; one retry policy decided by the error's kind (backoff, the wait a provider asks for, a hard stop for a bad key or no quota, the model told what was invalid); every attempt counted with the tokens the provider reports, kept per session and shown on the result page; keys removed from error text; a native Anthropic adapter; a stronger model asked once, only when a skill design still fails its checks after its repair; an opt-in response cache. | **Built; 755 backend tests (753 passed, 2 skipped; about 130 new), 53 UI unit tests (3 new); one live Gemini call and two live builds through the builder (one stopped at "requirements incomplete" because the model's quote was not verbatim, one finished with 30 checks passed). Also run live: Groq as a second provider (the fast tier on Groq, the rest on Gemini). Not verified: the Anthropic adapter and escalation with a real stronger model (mocks only), a real 429, the browser suite (not run). Not built: the tier benchmark (A4); escalation beyond the skill design** |
| M. Providers together | `LLM_FALLBACKS=provider:model,...` ([ai-engine.md](ai-engine.md)): when the first model is rate limited, out of quota, overloaded, unreachable or keeps failing the format, the next one answers; a bad key or a bad request never hands over, so a mistake still shows. Any provider, free or paid. `skillforge models [--test]` and `POST /api/provider/check` show what is set up, flag keys that nothing uses (with the line to add them), and test each model with one tiny call. The owner's setup is Gemini first and Groq behind it. | **Built; new backend tests for reading the setting, the handover rules, the models command and the API check; live: both models answered through the real configuration, a forced Gemini timeout failed over to Groq, and Groq's rate limits (8,000 tokens a minute) explain its 5 errors in a 10-run extraction comparison where Gemini was complete 10 of 10 (so Gemini stays the main model). Not verified: OpenAI, Anthropic, OpenRouter and Mistral as backups with real keys (mocks only)** |
| N. Hosted version | The same program on a link, for a phone or any computer ([hosting.md](hosting.md)): `SKILLFORGE_MODE=hosted` needs an access token (the server will not start without one) and puts a sign-in (signed cookie or bearer token, a lock after five wrong tries) in front of the whole API; install into server folders and the interactive docs are off; allowed host names are configurable. One Docker image serves the pages and forwards `/api/*` to the Python API, so there is one address and one cookie. `serve --host` beyond this machine is refused without it. A sign-in screen in the UI. Local use is unchanged and still the default. | **Built; 19 new backend tests (802 in all: 800 passed, 2 skipped), 57 UI unit tests, and the real-browser suite still passes 39 of 39. The image was built and run for real with Docker: sign-in, the 401/403 rules, a 3.6 MB upload through the forwarder, both models from inside the container and a real build all worked. Not verified: any real hosting service, https and the Secure cookie on a real address, the sign-in screen in a real browser or on a phone** |
| O. Component Factory, Phase 0 | The foundation for more kinds of builder ([component-factory.md](component-factory.md)): a kind registry (`skillforge/kinds/`, one kind so far: the skill), a library folder per kind, static checks that take a kind (only the definition-file check varies), builder sessions that carry a kind (migration 0003) and run the kind's own reading and building steps, `GET /api/kinds`, `?kind=` on the library routes, rescan and validate, and a kind picker and badge in the Builder (shown only when there is more than one kind). Two small skill improvements: a skill's permissions are written into `SKILL.md` as `allowed-tools` by code, and a front-matter key Claude Code does not know now warns. | **Built; 67 new backend tests (869 in all: 867 passed, 2 skipped because this account cannot create symbolic links), 8 new UI unit tests (65 in all), and the real-browser suite still passes 39 of 39. Nothing changes for skills; the tests prove the foundation with a fake second kind. Not verified: a real second kind (Phase 1 builds the first); `allowed-tools` and the list of front-matter keys against a live Claude Code (the list was read through a summarising fetch of the docs page on 2026-11-20). Not done: running `eval` from the web pages (it needs a job that is not a builder session), library tabs per kind, a `--kind` flag on the command line. `allowed-tools` is a grant: `Bash` is not narrowed to the skill's scripts** |
| P. Component Factory, Phase 1: Agent Builder | The second kind ([agent-builder.md](agent-builder.md)): describe a Claude Code subagent in words, answer only what is missing, approve, and get an `AGENT.md` (front matter `name`, `description` and an explicit `tools` line written by code; your rules, criteria and failure behaviour word for word) that is checked, kept in its own library (`library-agent`), exported, imported back identical and installed as one file in `~/.claude/agents`. The checklist is the same six items in agent wording; checks and one repair are decided by code; imported agents fail on a missing `tools` line and warn on `bypassPermissions`, `hooks` and `mcpServers`. The Library has an Agents tab and every page carries `?kind=`. | **Built; 37 new backend tests (906 in all: 904 passed, 2 skipped because this account cannot create symbolic links), 4 new UI unit tests (69 in all), reviewed by a fresh reviewer (no Critical or Important finding; two minors fixed after it: the risk diff now reads an agent's `AGENT.md` and `tools`, and library tabs no longer show stale rows), and the real-browser suite still passes 39 of 39 (its skill flows). Not verified: any run against a live model (the tests use a mock), an agent flow in a real browser, `tools` as a comma-separated string against a live Claude Code. Not done: `eval` for agents, unknown-key warnings for agents, risk-diff rules beyond `AGENT.md` and `tools`, a `model` choice, `--kind` on the command line** |
| Q. Component Factory, Phase 2: Plugin Builder | The third kind ([plugin-builder.md](plugin-builder.md)): **compose** a Claude Code plugin from skills and agents already in the library (no conversation, no model): `.claude-plugin/plugin.json`, a local marketplace file that points at the folder, `skills/`, `agents/` and a README; each component is read through the library (hash-verified and re-gated) so a damaged or failing one is refused; what the plugin can do (tools its skills and agents grant, scripts it ships and what they use) is computed by code and shown before it is kept; reserved names (`claude-`, `anthropic-`) are refused; the version `0.1.<n>` moves only when the content does; kept in `library-plugin`, exported, imported back identical, installed from a folder. API `POST /api/plugins/preview` and `POST /api/plugins`, a Plugins page, a Plugins tab in the Library. | **Built; 51 new backend tests (958 in all: 956 passed, 2 skipped because this account cannot create symbolic links), 8 new UI unit tests (77 in all), and a plugin built by this code passes Claude Code's own `claude plugin validate --strict` (2.1.325). The real-browser suite still passes 39 of 39 (run on free ports; its skill flows, including the install dialog this slice changed). Not verified: a real `claude plugin marketplace add` and `install` (they change your Claude settings, so you run them), the plugin page in a real browser. Not done: hooks, MCP servers, `userConfig`, `--kind` on the command line.** **An independent review (2026-11-20) then found nine real problems, all fixed and tested (`tests/test_plugin_review.py`, `test_library_review.py`, `test_names.py`): components were hash-checked but not re-checked (the docs said they were), the capability note called scoped Bash and unknown tools "read only", hooks and MCP servers in components or in a zip from outside went unmentioned, a version number could repeat after a rollback, a name with a trailing newline passed (every kind), Windows device names crashed an import, names that differ only by case or `./` collided, a backup could be overwritten within one second, and the composer page could show an old answer for a changed form. The risk diff now looks inside components** |
| R. Component Factory, Phase 3: MCP Builder (Python) | The fourth kind ([mcp-builder.md](mcp-builder.md)): describe a few tools; the model drafts them and **code** writes `server.py` around them (imports, signatures, per-tool annotations, `mcp.run()`), pins `mcp==2.3.0` and writes a README with the exact `claude mcp add` command. Checked by reading it: commands, code built from text, native code and a written key **fail** (the report never repeats the key), network, file writes, other packages, a computed environment name and an undefined name **warn**; the builder also fails a package outside the standard library, an undeclared permission, an unused import, made-up data and bad test cases; one repair kept only if not worse. Then the server is **started in the sandbox and called over the real MCP protocol** with a fixed harness, graded by code (image `skillforge-mcp:2.3.0`, built once by `python -m skillforge sandbox-build-mcp`); no sandbox, no image or a tool that needs the network means "not run" and a DRAFT, never "ok". Kept in `library-mcp`, exported, installed into a folder; the risk diff reads a server's code, tools and environment variables. | **Built; 118 new backend tests (1,076 in all: 1,074 passed, 2 skipped because this account cannot create symbolic links), 1 new UI unit test (78 in all), the real-browser suite still passes 39 of 39 (run on free ports). Checked against real tools: the SDK's names by a real install of `mcp` 2.3.0; a generated server started and called in a real container (two live tests); two real builds with the configured model, which found and fixed two defects a mock model could not (code that used modules it never imported, and a tool that returned simulated data). Not verified: the MCP flow in a real browser, a run against a live Claude Code (`claude mcp add` changes your settings). Not done: TypeScript, HTTP transport, resources and prompts, OAuth, packages beyond the standard library, file writes, commands, `--kind` on the command line.** **An independent review (2026-11-20) found the first checks too weak, all fixed and tested (`tests/test_mcp_security.py`, `test_mcp_builder_hardening.py`, a live forgery test in the real container; 1,304 backend tests in all): an encoding declaration hid code from the checks, any file beside `server.py` ran unchecked, plain alternate spellings of running a command, writing files, reaching the network and reading the environment passed, keys written in pieces passed, a forged sandbox pass was possible, a tool name could be written into the file as code, and `requirements.txt` was never read. The analyser now resolves aliases and flags the import; a server the builder writes may import only an allow-list of safe standard-library modules. The checks remain a reading by syntax and cannot prove a file safe** |
| S. Component Factory, Phase 4a: MCP servers in plugins | A plugin can carry **MCP servers from the library** ([plugin-builder.md](plugin-builder.md), [plan](superpowers/plans/2026-11-23-plugin-mcp-phase-4a.md)): the composer writes `servers/<name>/`, a root `.mcp.json` that starts each (`python ${CLAUDE_PLUGIN_ROOT}/servers/<name>/server.py`) and one `sensitive`, `required` `userConfig` option for **every environment variable the server's code reads**, passed as `${user_config.KEY}` (a value is never written; two servers never share an option). What each server can do (tools, network, file writes, started programs, variables) is read from its code by syntax and said plainly, never "read only". The plugin's check runs each server through the MCP checks and checks that `.mcp.json` starts **only what is shipped, in the composed form**: in a plugin from outside, another command, a URL, extra keys, a literal `env` value, or a variable the server never reads is warned about with the command shown (a value never is), an undeclared `${user_config.X}` fails, and a `userConfig` key Claude Code refuses fails the manifest. The risk diff calls a new server, a changed start command, a new entry and a newly passed variable riskier. The composer page lists MCP servers and shows "Programs this plugin starts". | **Built; 56 new backend tests (1,358 passed, 2 skipped because this account cannot create symbolic links), 4 new UI unit tests (82 in all) and a clean typecheck. Checked against the real tool: Claude Code 2.1.325's `claude plugin validate --strict` was used to settle the format (it reads `.mcp.json`, refuses a `userConfig` key with a dash, dot, space or leading digit, fails an undeclared `${user_config.X}`), and a plugin composed from two real library servers (one reading a key) passes with exit 0. A review of my own check found one loophole (an option could set `PYTHONPATH` on a server) and it is fixed with a test. Not verified: a real `claude plugin install` (it changes your settings) so what Claude Code does when it starts the server and asks for the options was not seen; the new page section in a real browser (the 39 browser behaviours were not re-run); no independent review of this slice. Limits: the command is plain `python` (the package must be installed by you), Python servers from the library only, no hooks** |
| T. Component Factory, Phase 4b: hooks in plugins, from a catalogue | A plugin can carry **hooks, only from a fixed catalogue** ([hook-catalogue.md](hook-catalogue.md), [plan](superpowers/plans/2026-11-23-plugin-hooks-phase-4b.md)): `skillforge/hookcatalog/` holds three vetted hooks (block reading or changing secret files, block forced `git push`, log which tools were used) as short standard-library scripts, each with a fixed event, matcher and timeout and typed **options** that reach the script as separate exec-form arguments (a pattern that cannot start with a dash or be only wildcards, a cap on how many), so an option can never become code. Nobody types a hook and no model writes one. The composer writes `hooks/hooks.json` and the catalogue's script unchanged and describes every hook plainly (when it runs, whether it can block, what its script can do, what was chosen), never as read-only. The plugin's check **recognises a hook only when it is exactly a catalogue hook**: event, matcher, timeout, command, arguments and a script whose SHA-256 is the catalogue's (line endings ignored, earlier revisions listed); anything else in a plugin from outside is warned about with the command shown, and a plugin with nothing it can describe has no content. The risk diff calls a new hook, a changed trigger and a script that is no longer the catalogue's riskier, and now also compares code a plugin ships outside its components. `GET /api/hooks`, a Hooks card and a "Hooks this plugin runs" preview section. A script that cannot read what Claude Code sends it does not block and says so (exit 1), so a changed format is noticed, never silently ignored. | **Built; 180 new backend tests (1,538 passed, 2 skipped because this account cannot create symbolic links), 6 new UI unit tests (88 in all), a clean typecheck and the real-browser suite passing 42 of 42 (3 new composer behaviours; the plugin page had never been driven in a browser before). **Run by real Claude Code (2.1.325, one session, `--plugin-dir`, no settings changed):** a `Read` of a dummy `.env` was blocked by `block-secret-files` and `git push --force` by `block-force-push`, each with its own reason shown to the model, an ordinary read passed, and `log-tool-calls` wrote its line to the plugin data folder (removed afterwards): this settled the field name `tool_input.file_path`, the exec form with `python` and `${CLAUDE_PLUGIN_ROOT}` on Windows, and that exit 2 blocks. `claude plugin validate --strict` also accepts a plugin of all three. Checking my own work found a gap (git accepts `--forc` for `--force`, and the first script let it through) and it is fixed with tests, the pin test having caught the edit. Not verified: a real `claude plugin install`, an interactive session, `NotebookEdit` and the `PowerShell` tool name, a machine where `python` is not on the PATH; the MCP picker in a browser; no independent review of 4a or 4b. A hook is a policy aid, not a security boundary: it matches names and text (`cat .env` through the shell is not seen) |

Product | Next: the TypeScript half of Phase 3 (MCP in TypeScript), then the other differentiators (evidence-linked skills with code-level drift; the canary behaviour scan) and the rest of [ui-and-database-plan.md](ui-and-database-plan.md): H5 suggest/graph pages, Settings. | **Next: Phase 3b (the MCP builder in TypeScript), or an independent review of Phases 4a and 4b, or the next differentiator ([differentiators.md](differentiators.md)), or H5** |
