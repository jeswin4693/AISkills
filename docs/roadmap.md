# Roadmap

SkillForge AI does three things, built in this order:

```
 Repo --> UNDERSTAND --graph facts--> SUGGEST --ideas with evidence--> BUILD --> skill packages
          (no AI)                     (AI + graph)                      (AI + templates)
```

| Slice | What | Status |
|---|---|---|
| A. Understand | Repository graph: functions, calls, imports, impact, duplicates, hotspots, dead-code candidates. Python + TypeScript/JavaScript. Incremental cache. CLI. Tests. See [graph.md](graph.md). | **Built** |
| B. Providers + Suggest | One `LLMProvider` interface (Gemini and OpenAI through one adapter, plus a mock for tests). A review pass and an ideas pass over a fact sheet from the graph. Every suggestion must cite real graph nodes; uncited ones are dropped. See [suggest.md](suggest.md). | **Built; 83 offline tests; verified live with Gemini** |
| C. Build | Requirement text, clarifying questions (completeness decided by a checklist, answers backed by verified quotes), approval, skill definition, generated files, `report.md`. A suggestion can seed it. See [build.md](build.md) (original plan: [step1-proposal.md](step1-proposal.md)). | **Built; 127 offline tests; verified live with Gemini** |
| D1. Safety | Static validators for any skill folder (hidden text, attack wording, scripts versus declared permissions, structure) run on every build; a Docker sandbox runner that fails closed. See [validate.md](validate.md). | **Built and proven: 14 real-container tests (Docker in WSL) prove the locks and the per-language runs; 232 tests in total** |
| E. Any language | The graph, validators and sandbox work beyond Python and TypeScript: 45 languages at three honest levels (full, standard, basic), Java/Go/Rust/C/C++/C#/Ruby/PHP/Kotlin with resolved imports and calls, grammars loaded on demand with an offline mode, interpreter languages runnable in the sandbox. See [languages.md](languages.md). | **Built and tested** |
| F. Scripts | `build --scripts`: the model writes helper scripts and test cases, code checks them, every case runs in the sandbox, one repair attempt shown the real output. A case passes only if it ran; untested scripts make the skill a DRAFT. See [scripts.md](scripts.md). | **Built; 273 tests in total (36 offline script tests, 5 more real-container tests); verified live: real containers and Gemini** |
| G. Library | `library import` (static checks first, refused if one fails; folders and untrusted zips), numbered versions with a SHA-256 manifest (tamper-evident), `diff`, `rollback` (adds a version), deterministic `export` zip, `install` to `.claude/skills` (explicit target, backup before `--force`), opt-in `--test-scripts` re-run in the sandbox. See [library.md](library.md). | **Built and tested; checked on the real CLI on Windows; not yet used on skills from other people** |
| H1. API | Local HTTP API (FastAPI, `serve`, 127.0.0.1 only): library, validate, sandbox status and languages endpoints; Host and Origin checks against DNS rebinding and cross-site requests; capped in-memory uploads. See [api.md](api.md). | **Built and tested; checked against a real running server (curl)** |
| H2. Database + builder sessions | SQLAlchemy + Alembic (SQLite first, one URL setting for another database); the skill builder as a session across requests: questions, answers, approval, then background jobs with progress, retry, save to the library. Same rules as the CLI (checklist in code, verified quotes, approval before building). See [database.md](database.md), [api.md](api.md). | **Built and tested (offline, incl. real threads); verified live with Gemini: a full conversation produced a skill with 21 checks passed. Not tried: PostgreSQL, building with scripts over HTTP with a real sandbox** |
| H3. Web UI shell + Library | `frontend/`: Next.js 16 + React 19 + TypeScript + Tailwind 4. App shell with a live status panel; Library page (import by choosing or dropping a .zip, results in plain words, refusals with the failed checks); skill page (versions, files, checks, export, install, restore); compare page (diff). See [ui.md](ui.md). | **Built; typecheck clean, 20 unit tests, and 19 behaviours checked in a real Edge browser against the real API; not tested in other browsers or with a screen reader** |
| H4. Builder page | `/builder`: describe a skill, answer only what is missing, approve a requirement shown beside the person's own verified words, watch the build, see each acceptance criterion beside the tests that cover it, save through the checked import. Model not set up, failures with retry, DRAFT gating, past sessions, discard. See [ui.md](ui.md). | **Built; 39 unit tests and 31 real-Edge behaviours with a scripted fake model; verified live once (2026-11-19): the whole conversation in a real browser against real Gemini, 21 s, saved as v1. Not verified: the scripts checkbox with a real sandbox, other browsers** |
| C1. Task Plan | `skillforge plan "<task>" --repo <path>`: reads a request and plans it before any work: what it contains (verified quotes) and does not say (questions, assumptions), the tier from measured graph facts, the process phases and stop triggers, the rules that apply (file:line, not enforced yet), and a token plan (named functions as exact line ranges, capped tests, a budget). Read-only; `--no-ai` sends nothing. See [task-conductor.md](task-conductor.md). | **Built; 79 offline tests; run live once with Gemini on this repo (and that run exposed and fixed two weaknesses). Not built: answering and approving a plan, a web page, turning plans into skills, enforcement** |
| I. Risk diff + rescan | The first differentiator ([differentiators.md](differentiators.md)): every new version of a skill is compared with the one before and **what got riskier is listed** (scripts that gain the network or commands, new permissions, attack-like wording and hidden markup, new web addresses, a changed description), and `library rescan` runs today's checks on every stored version. Code only, no model, nothing is run; it never says "safe". CLI (`diff`, `import`, `rescan`), API (`/diff`, `/import`, `/api/rescan`) and the Library, skill, Compare pages. See [library.md](library.md). | **Built; 47 offline tests (pure comparison, rescan, CLI, API); 38 behaviours in a real Edge browser, 7 of them new; mutation-checked (4 deliberate breaks, 1 survived and a test was added). Tested on synthetic skills only: the false-alarm rate on real skills is not measured** |
| J. Stronger skills | The builder writes skills that **work better and cost less to use**: the description is built by code from trigger phrases (so it says *when* to use the skill); your approved rules, acceptance criteria and failure behaviour are carried into SKILL.md word for word and checked; a worked example; what is only for people (limitations, permissions) moved to the README; quality checks for vague wording, inputs no step uses, outputs no step makes, over-long steps and garbled examples; the one repair attempt also fixes quality warnings and never makes the skill worse; the token cost (always loaded / when used / on demand) in every result. See [build.md](build.md). | **Built; 33 new offline tests (555 in all), 2 new UI unit tests and 1 new browser behaviour, 7 deliberate code breaks all caught; checked live with Gemini twice on the same job as an installed skill (SKILL.md about 392 to 404 tokens against 536, and the live runs exposed three weaknesses that were then fixed). Not measured: whether an agent does the job better with the new skills (test cases are still never run against an agent); the always-loaded text grows by about 11 to 20 tokens** |
| K. Test harness | `skillforge eval <folder>` and `build --eval`: a skill's own test cases are run against a model **with the skill and without it**, and code grades the replies with seven kinds of simple check (no model judges). It says whether the skill helped, adds nothing for its tokens, made things worse, or had too few cases; a skill that fails its own tests gets one repair shown the real replies. Every built test now carries the exact message to send and its checks. Text-only skills only (a model with no tools is not an agent). See [evaluate.md](evaluate.md). | **Built; 66 new offline tests (626 in all), 9 deliberate code breaks all caught; run live with Gemini on the commit-message job: with the skill 6 of 6, without it 2 of 6, because without it the model breaks the person's own 50-character rule (single runs vary: 0 of 3 once). Not built: running it from the web pages; tools-using skills; a stronger or independent judge of tone and facts. The tests are written by the model that wrote the skill** |
| L. AI engine | One model service for every builder ([ai-engine.md](ai-engine.md)): the model is chosen by kind of work (fast, design, code, actor) from optional settings, with Gemini the default for all of them; one retry policy decided by the error's kind (backoff, the wait a provider asks for, a hard stop for a bad key or no quota, the model told what was invalid); every attempt counted with the tokens the provider reports, kept per session and shown on the result page; keys removed from error text; a native Anthropic adapter; a stronger model asked once, only when a skill design still fails its checks after its repair; an opt-in response cache. | **Built; 755 backend tests (753 passed, 2 skipped; about 130 new), 53 UI unit tests (3 new); one live Gemini call and two live builds through the builder (one stopped at "requirements incomplete" because the model's quote was not verbatim, one finished with 30 checks passed). Also run live: Groq as a second provider (the fast tier on Groq, the rest on Gemini). Not verified: the Anthropic adapter and escalation with a real stronger model (mocks only), a real 429, the browser suite (not run). Not built: the tier benchmark (A4); escalation beyond the skill design** |
| D2. Product | Rest of the plan in [ui-and-database-plan.md](ui-and-database-plan.md): H5 suggest/graph pages, Settings. Then the other differentiators (evidence-linked skills with code-level drift; the canary behaviour scan). Agent Builder last. | **Next: choose the next differentiator ([differentiators.md](differentiators.md)), or H5** |

Why this order: slice A needs no model, no key and no network, so it is fully testable offline and every
later slice stands on it. Generated code is never executed until the sandbox in slice D exists.

Decisions behind this are in [decisions.md](decisions.md).
